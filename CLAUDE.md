# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Django backend for a private, auth-gated portal for a band ("Rolling Sloans"): who's in the band each semester, what they play, the setlist, and the rehearsal schedule. The repo is public as a showcase, but must never contain real member data or credentials — see "Privacy constraint" below, it governs how you write code and tests here more than typical style rules would.

## Commands

```bash
# Setup
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# Run

# Deploy-config smoke test (also covered by identity/tests/test_deploy_check.py)
python manage.py check --deploy

# Frontend (cd frontend/ first)
npm ci
npm run build       # writes frontend/dist/, which SpaIndexView reads
npm run lint
npm run typecheck
npm run test
npm run format:check

```

The Django test suite passes on a checkout that has never run `npm install` — `config.checks.spa_build_output_exists` only runs under `--deploy`, never a plain `test`. CI (`.github/workflows/ci.yml`) runs four jobs: `ruff check .`; `manage.py test --parallel` against a real Postgres service; a node job (`npm ci`, lint, format check, typecheck, the Vitest suite, then `npm run build`); and a `build` job that installs both toolchains, builds the frontend, runs `manage.py check --deploy` under production-like env vars, and `collectstatic` — plus a grep-based scan that fails the build on any committed `.env`/`.pem`/`.key`/`id_rsa`/`id_ed25519` file. `build.sh` runs the same frontend-build-then-`collectstatic` order for a real deploy.

## Architecture

Two Django apps today:

- **`identity`** — auth and account lifecycle. `Person` (`identity/models.py`) is a custom `AbstractBaseUser` (`AUTH_USER_MODEL = 'identity.Person'`) keyed on email, with a single `is_admin` flag that `Person.save()` mirrors onto `is_staff`/`is_superuser` — there's no separate Group/Permission scheme. Accounts are never self-registered: `identity/services.py`'s `create_person_with_temp_password()` is the only path to a loggable-in `Person` (besides the Django admin), setting a real, immediately-usable password via `set_password()` and flagging `must_change_password=True` — the plaintext temp password is returned exactly once for the admin's response to relay verbally or by text, never emailed and never logged (issue #482, ADR 0018). `apply_password_reset()` is its sibling for an *existing* Person, reached from `/members/<pk>/` (issue #483): same generated temp password and forced-change flag, refused for a self-reset (the admin's own self-serve change-password flow covers that) and for a deactivated target. `generate_temp_password()` draws twelve characters from an alphabet that drops visually-ambiguous characters (`0`/`O`, `1`/`l`/`I`), since the password travels by voice or text rather than copy-paste through a link. `identity/urls.py` is down to two routes (issue #485, from four): login and logout — `password-reset/` and `set-password/<uidb64>/<token>/`, along with `PasswordResetRequestView`/`PasswordResetConfirmView` and the invite/reset email templates, are deleted outright now that there's no emailed link to request or confirm. Change password remains in the SPA (issue #333) as the one auth act performed *with* a session; it's also what clears `must_change_password` (`clear_must_change_password()`, issue #484), enforced as a request-level redirect gate rather than a client-side check so a Person with the flag set can't route around it. The project's first rate limit lives beside `is_login_rate_limited()` in `services.py` (failed sign-ins, keyed on submitted address and requesting IP) — a windowed count of `LoginAttempt` rows, deliberately not a cache, since `CACHES` is unconfigured and `LocMemCache` would silently multiply any limit by the gunicorn worker count. Its email-specific sibling, `is_auth_email_rate_limited()`/`AuthEmailRequest`, is retired along with the email flow it protected (issue #485) — there is no more outbound auth email to throttle.
- **`scheduling`** — the domain described in `CONTEXT.md`, now largely implemented: `Semester`, `Role`, `Membership`, `PersonRole` (person-level, not semester-scoped — ADR 0014), `Song`, `SongRoleRequirement`, `SongRoleAssignment`, `Rehearsal`, `RehearsalPattern`/`RehearsalTime`/`SkipDate` (the date-generator's saved pattern), `RehearsalSong`, `Conflict`, `ConflictWindow`, `Recording`, `Backup`. Read `CONTEXT.md` before adding any scheduling model or field — it defines the project's ubiquitous language (e.g. "Song" is scoped to one semester, never reused across terms; "Running Order" is a rehearsal's sequence, distinct from the Setlist's concert position).

### How a scheduling request is put together

The non-obvious shape here is that **`scheduling/services.py` is the read-model layer, not just a write layer.** Views are deliberately thin: they resolve the viewing Semester, call service functions, and hand the returned dataclasses (`AssignmentMatrix`, `RehearsalSchedule`, `SongPerformer`, `AttendanceSuggestion`, `RecordingSlotGroup`, …) straight to a template. Derived reads — attendance inference, rehearsal progress, the Song×Role×Person matrix, recording grouping, presigned R2 URLs — live in services, so put new derived logic there rather than in a view or a template tag.

- **Auth is structural, not per-view.** `config/views.py` defines `BaseView` (a `LoginRequiredMixin` every non-auth view in the project mixes in, so none can forget to gate itself) and `AdminRequiredMixin` (adds a 403 for a logged-in non-admin, used by every admin-only view or `/api/` endpoint — see `ApiView`/`AdminApiView` below). Mix one in ahead of the Django generic class; don't hand-roll a gate.
- **Route shape**: an SPA client route (`frontend/src/routes.tsx`) fetches its whole read model from one `/api/` route (`scheduling/api_urls.py`) — band-wide reads at `/`, `/schedule`, `/setlist`, `/songs/:songId`, `/members`, `/members/:personId`, admin-only Conflict adjudication at `/conflicts` and `/conflicts/:rehearsalId`, and Recordings folded into `/members/:personId` (self-view only) rather than its own destination. Admin *editing* of band-wide data lives on the read surface it edits, not on a separate route: `/schedule/edit`, the Setlist and Song Cast/Requirements in-place edit modes (plus the Setlist's own inline per-cell cast popover), the Roster editor and the per-Rehearsal Backup grid are all reached from the page they edit, gated by `AdminApiView`/`AdminRequiredMixin` server-side rather than by a client-side route guard. Neither the client routes nor the `/api/` routes carry a `/manage/` prefix — admin-ness was never signalled by URL, only enforced by the gate, so dropping the prefix (issue #341) changed no permission. `/manage/semesters/` and the four-step `semesters/setup/<pk>/` wizard have **no route at all** now: #329 replaced the list-and-buttons page with three sidebar controls (Viewing dropdown, New semester, Manage semesters as popups), and #332 replaced the wizard with a derived setup checklist on Home — both destinations were decided away, not rebuilt 1:1, per the rule that **a destination earns a route by what its most dangerous action costs, not by how much content it has** (which is also why adjudication keeps two routes while Semester management now has none). `/schedule` is the **single** member-facing page (issue #190): it absorbed `/me/conflicts/` outright, so a member's own availability — declaration, verdict, note, and the declare/edit/delete controls — folds inline into the Rehearsal it concerns. There is still **no** `/profile`: `/members/:personId` is the single per-person page, read-only for a teammate and editable in place for your own id, and the nav's Profile tab points at your own id. Its field-by-field verdicts live in `docs/person-page-visibility.md` (ADR 0005). `/accounts/manage/people/` is **retired** (issue #342, ADR-0017): `PeopleView`, `PersonToggleAdminView`, `PersonResendInviteView`, and the `/manage/people/` routes are deleted, their invite/resend-invite affordance having already been fully duplicated by the Roster editor (#336), and its one genuinely uncovered job — admin grant/revoke — now landed as `PersonAdminStatusApiView` (#467) on `/members/:personId`, alongside a new Deactivate/Reactivate lifecycle act (`PersonDeactivationApiView`/`PersonReactivationApiView`, #469) for off-boarding, which the old page never had at all, and a Reset-password action (`PersonPasswordResetApiView`, #483, ADR 0018) that absorbs `resend_invite()`'s old job — it works on anyone at any time, not just a stuck invite. Admin grant/revoke is a direct `apply_admin_status_change()` call (no Buffer — one field, no derived fallout), guarded against self-revoke and revoking the last Person who is both `is_admin` and active; Deactivate is a plain `apply_person_deactivation()` call too, not a Pending Buffer/Preview surface (ADR-0008's shape is for multi-field edits; this is one field with a client-side confirmation sourced from data `/members/:personId` already loads) — guarded against self-deactivation and deactivating the last active admin, and terminating any live session immediately rather than only blocking future logins. The Django admin is not the only surface outside the SPA — the non-SPA `identity` auth routes (login, logout) remain too, down to just those two since issue #485 removed the rest.
- **"Which Semester is this request scoped to" is answered in exactly one place**: `services.get_viewing_semester(request)`, for reads *and* writes. Reuse it; never re-derive recency, and never read `id` or `created_at` as a proxy for "the semester". Its sibling `services.get_live_semester()` (greatest `published_at`, nulls excluded, else `None`) answers the different question "what do members see" — keep the two distinct, per ADR 0010. `services.set_viewing_semester(request, semester)` records an admin's session selection (`None` clears it). "Current semester" is a **retired term** — a `Semester` with a null `published_at` is a *draft*, and the one with the greatest `published_at` is the *Live Semester*.
- **The non-live Semester banner comes from the envelope, not from a per-page fetch.** `services.semester_banner_for(request)` still answers "should this admin see a draft-editing warning", but its presentation moved from a Django context processor (`scheduling/context_processors.py`, deleted by issue #341) to `context.semester_warning`, a key `scheduling/serializers.py:serialize_context()` sets on **every** `/api/` response's envelope. The guarantee issue #169 built the context processor for — a per-view key is one a view can skip — now holds because the envelope is the return type: `ApiView.read_response()`/`write_response()` attach `context` themselves, so a new endpoint cannot omit it either. The switcher is a sidebar control (issue #329) posting to `POST /api/semesters/select/`, fed by `context.semester_options` — deliberately a plain request against a stable endpoint, not something that depends on a particular component staying mounted, so which Semester an admin edits never hinges on a script re-render (issue #169's original concern, restated for the SPA).
- **Every admin edit surface is the same three-part shape: Buffer → `preview_*()` → `apply_*()`.** A surface collects unsaved edits into a frozen dataclass Pending Buffer (`RosterEditBuffer`, `AssignmentEditBuffer`, `RehearsalEditBuffer`, `AdjudicationBuffer`, `SongRoleRequirementBuffer`, `SongCastEditBuffer`, `SemesterDefaultsReapplyBuffer`, `SetlistEditBuffer`), which two functions consume: `apply_*(buffer, *, viewing_semester, …)` commits it, and `preview_*(buffer, …)` returns a `*Fallout` dataclass describing what saving would do. `preview_*()` **calls the real `apply_*()`** and the transaction is rolled back around it (ADR 0008) — there is no second, pure implementation of any derivation. On the wire (ADR 0012), a `build_*_buffer_from_request()` function per surface (`scheduling/api_builders.py`) is the *one* place a submitted JSON body becomes that surface's Buffer, called by both its `preview/` and `save/` endpoint — never construct a Buffer from the request body a second way, or ADR 0008's guarantee (preview and save can't disagree because they run the same code) breaks one layer further out than it used to. Follow the existing surfaces when adding one: a new Buffer, a `Stale*SemesterError`, an `apply_*`, a `preview_*`, a `*Fallout` with a `block_message`, a `build_*_buffer_from_request()`, and a `preview/`/`save/` endpoint pair. One deliberate exception to the staleness half: `SongCastEditBuffer` pins `Song.updated_at` rather than `Semester.updated_at` (ADR 0019), because a cast edit is scoped to one Song and two admins casting two different Songs have genuinely not collided.
- **`config/views.py:PreviewMixin` owns the rollback**, so a preview view never writes its own `transaction.atomic()`. On the pre-cutover portal it mixed in ahead of `AdminRequiredMixin`; every surviving surface is `/api/`, so it now mixes in ahead of `AdminApiView` as `config/views.py:AdminPreviewApiView(PreviewMixin, AdminApiView, View)` — mix that in and override `run_preview()`. The mixin wraps the call and ends with `transaction.set_rollback(True)` — never a sentinel exception. Every preview endpoint must have a test calling `scheduling/tests/preview_helpers.py:assert_preview_writes_nothing`, which checks row counts, `Semester.updated_at`, `mail.outbox` and that R2's `delete_object` was never reached; that helper is the only thing verifying the `on_commit()` rule holds for a new surface.
- **Song position mutations must hold a lock.** `apply_setlist_edits()`, `apply_rehearsal_edits()` and every other position-renumbering `apply_*()` open with `Semester.objects.select_for_update().get(pk=…)`, row-locking the `Semester` inside `transaction.atomic()` so concurrent creates/moves can't collide on `unique_song_position_per_semester`. Any new code that renumbers positions needs the same treatment — and note `RehearsalSong` has a `UniqueConstraint(rehearsal, order)`, so a reorder cannot write new `order` values row by row.
- **`RehearsalSong.save()` derives and persists `start_time`/`end_time`** from `order` + `slot_count` + the Semester's `default_song_slot_count` — never from `Song.length`, which is a display field with no scheduling authority. A slot is an equal share of the Rehearsal's window, not the song's running time, so a 3-minute song and a 7-minute one occupy identical slots (rehearsing a song takes far longer than playing it once); don't wire `length` into `slot_count`. Reordering a rehearsal therefore changes *when each song happens*, which changes which `ConflictWindow`s overlap it — relevant to anything computing availability.
- **`services.deal_running_orders()`/`shuffle_rehearsal_running_order()` (issue #223) never re-deal a past Rehearsal, and never touch a "pinned" row.** A past Rehearsal is excluded outright (generation cannot rewrite history, mirroring the date generator). A row is pinned — held at its exact identity, `order` and `slot_count`, with the dealer filling every other slot around it rather than through it — for either of two independent reasons: it carries a Recording (so a bulk run can never invalidate an upload's timing), or its `slot_count` was hand-raised above the dealt default of 1 (an admin-only manual knob the generator never clobbers). Both functions are pure reads (no `apply_schedule_generation`, deliberately: see `RehearsalDeal`'s docstring) that fill the Rehearsal editor's existing Pending Buffer the same way a hand-edit does; only `apply_rehearsal_edits()` ever writes a `RehearsalSong` row — and that manual path deliberately allows deleting, moving or re-slotting a pinned row, which the dealer refuses (commented at both sites).

Two supporting modules sit beside the services layer rather than inside it: `scheduling/fields.py` (`SongLengthField`, the `M:SS`/`H:MM:SS` round-trip parser for `Song.length`, shared by the setlist grid and the Spotify import) and `scheduling/spotify.py` (read-only Client Credentials playlist fetch that *returns* setlist row data for the edit buffer to append — it writes nothing, and a missing `SPOTIFY_CLIENT_ID`/`SPOTIFY_CLIENT_SECRET` degrades to a message, not an error).

### Frontend

A React/TypeScript single-page app under `frontend/` — see `frontend/CLAUDE.md` for the bundler/no-CDN/testing/static-serving conventions. The one prohibition worth repeating here since it's enforced repo-wide, not just under `frontend/`: **no CDN, ever** (privacy grounds — a CDN would announce every member's IP and referer to a third party), checked by `scheduling/tests/test_static_assets.py`.

Two backend pieces make the SPA work and matter even to a session that never opens `frontend/`: `config/views.py:SpaIndexView` reads Vite's `manifest.json` per request and serves the hashed script/style tags it names — never a static `index.html` — and `config/urls.py`'s catch-all routes every non-`/admin/`, non-`/accounts/`, non-`/api/` path to it. And `STATICFILES_DIRS` in `config/settings.py` has two entries, not one — the top-level `static/` and `frontend/dist` kept as its own physically separate entry, so Vite's `assets/` subdirectory can never shadow anything else's filenames.

#### The `/api/` layer (issue #326, ADR 0012)

Every `/api/` view inherits `config/views.py:ApiView` (or `AdminApiView`, which layers `AdminRequiredMixin` ahead of it for an admin-only endpoint) — the gate lives on the base class every endpoint already subclasses to exist, the same shape `BaseView`/`AdminRequiredMixin` used for the pre-cutover portal.

- **401, never a redirect, for an unauthenticated request.** `ApiView.handle_no_permission()` answers `{"error": "authentication_required"}` at 401 rather than `LoginRequiredMixin`'s redirect — `fetch()` follows a 302 transparently, so a redirect would hand an expired session's caller a 200 carrying an HTML login page and a `.json()` parse failure with no visible cause. `AdminApiView` does the parallel thing for a logged-in non-admin: a JSON 403, never a redirect.
- **Every response wears the `{context, data}` envelope** (a write response also carries `ok`/`errors`/`non_field_errors`/`fallout`/`values`). `ApiView.build_context()` → `scheduling/serializers.py:serialize_context()` returns the viewer, the viewing Semester and its status, the Live Semester, the full Semester picker, `semester_warning` (the non-live banner, see above), and an admin-only `pending_conflict_count`. `read_response()`/`write_response()` attach it themselves, so a new endpoint cannot forget it — the same guarantee `semester_banner` used to enforce as a context processor, now enforced by the envelope being the return type.
- **A rejected Pending Buffer is HTTP 200, not 400.** A stale row, a blocked removal, a validation failure — these are well-formed requests whose answer is "no, and here is why", rendered inline via `ok: false`/`errors`/`non_field_errors`/`values`. `400` is reserved for a body `parse_json_body()` can't decode as JSON at all; a `semester_id` that doesn't match the viewing Semester is its own hard 409, answered before the surface's `preview_*()`/`apply_*()` is ever called.
- **Hand-written serializers, and `dataclasses.asdict()`/`model_to_dict()` are banned** (ADR 0005, enforced mechanically by `scheduling/tests/test_prohibited_serializer_helpers.py`). Every serializer function names every field it emits; an emit-everything helper is a rule that says "ship whatever this object happens to carry", and the day a new field lands on `Conflict` or a Buffer dataclass it would reach the wire with no line of code that decided that was safe.
- **Hand-written TypeScript types** (`frontend/src/api/types.ts`), for the same reason: a generator pointed at the Django models would reintroduce the emit-everything problem one layer up. A new field reaching the wire costs three edits — the serializer, the TS type, the component reading it — on purpose.
- **One endpoint per surface for a read, endpoint-per-interaction for a write.** `GET /api/schedule/` returns `/schedule`'s whole read model in one round trip rather than several REST calls assembled client-side; `POST /api/setlist/preview/`, `POST /api/setlist/save/`, `POST /api/members/roster/roles/`, etc. are one endpoint per admin *interaction*, mirroring the Buffer surfaces they front. Resource-shaped REST was rejected: it costs 3–5 round trips per page, and it would push ADR 0005's privacy verdicts and `is_role_mismatch` (ADR 0002) out of `services.py` and into the client.

**Read `docs/adr/*.md` before touching related behavior** — each records a deliberate rejection of the "obvious" alternative:
- `0001` — `Song` and `Membership` are re-created fresh per `Semester`; only `Person` persists across semesters. Amended by issue #375 (ADR 0014): Role declarations no longer follow this scoping — see `0014` below.
- `0002` — a `Role Assignment` whose Role isn't among the Person's declared `PersonRole`s (person-level, per ADR 0014) is saved anyway and flagged `is_role_mismatch`, never hard-blocked (admins are the sole authors and need to assign ahead of profile updates).
- `0003` — the Dress Rehearsal's songs are derived live from the current setlist at read-time, not snapshotted into `RehearsalSong` rows, so it can't go stale if the setlist changes after scheduling.
- `0004` — `Recording` files live in a private R2 bucket; uploads go client→R2 via a Django-issued presigned PUT, and playback uses short-lived signed URLs — never public objects, never proxied through the Django app server.
- `0005` — `Conflict` data (especially the free-text `reason`) is never rendered on a member-facing surface, admin viewers included; admins read it only through admin-only surfaces. Field-by-field verdicts for `/members/` and `/members/<pk>/` live in `docs/person-page-visibility.md`.
- `0006` — Dress Rehearsal attendance is mandatory, so no `Conflict` may point at a Rehearsal with `is_full_setlist=True`. Enforced in `Conflict.clean()`/`save()`, `declare_conflict()` and `future_rehearsals_for()`; deliberately **not** by a DB constraint, which cannot reach through the `rehearsal` FK. The other direction is guarded too: `Rehearsal.clean()`/`save()` refuse a flip to `is_full_setlist=True` on a Rehearsal that already has `Conflict` rows, with a count-only message (never who or why, per ADR 0005) — no ModelForm editing a Rehearsal has its own copy of that check.
- `0007` — a `Backup` (one Person covering a Role on a Song at one Rehearsal) is **its own model anchored on `RehearsalSong`**, not a nullable `rehearsal` FK on `SongRoleAssignment`, which would overload a table `CONTEXT.md` defines as a fact about a *Song*. The anchor depends on ADR 0006: the Dress Rehearsal has no `RehearsalSong` rows, so Backups are impossible there — fine only while no `Conflict` can point at it. `covering_for` is an advisory nullable FK to `Person` (`SET_NULL`), never load-bearing: a Backup with no standing assignee is legal and a withdrawn `Conflict` leaves the Backup standing. `attendance_for()` counts Backups; `performers_for(song)` must not. Per ADR 0005 the covered person's name is **admin-only**, though the Backup itself shows on the member-facing Schedule. Built: `Backup` in `scheduling/models.py` (with a live, never-stored `is_stale()`), surfaced as `AssignmentMatrixEntryKind.BACKUP` entries in the assignment grid.

- `0008` — unsaved admin edits **preview by running the real `apply_*()` inside `transaction.atomic()` and rolling it back**, never by reimplementing derivation in JS or as pure functions over unsaved instances (every derivation — `_prior_slots`, `_compute_is_role_mismatch`, `attendance_for`, `breaks_for` — reads the DB, so purity would mean two implementations of six read paths). Consequence: **every irreversible external side effect must be registered with `transaction.on_commit()`**, never called inline, or a preview really sends the email and really deletes the R2 object. Preview endpoints are POST-only siblings of their surface, take no `_lock_semester()`, and use a savepoint plus `transaction.set_rollback(True)` so an invalid buffer still renders. Built, and now the shape of every admin edit surface — see the Buffer → preview → apply bullet above.
- `0010` — the **Live Semester is the greatest `published_at`** (nullable; null = draft), with `created_at` for chronological ordering — no `status` enum, no partial unique constraint, no singleton pointer row, no unpublish, no `start_date`/`end_date`. Publishing stamps `published_at`; rollback is re-publishing an older Semester through the same code path. An admin's session selection governs **writes as well as reads**, so a `/manage/` write while a draft is selected lands on the draft; a stale or demoted selection falls back silently to the Live Semester, and only admins get the "nothing published, show the newest-created" fallback.

- `0011` — deleting a `Semester` is a **hard delete**, cascading to every scheduling row and to the R2 objects its `Recording`s named (keys collected *before* `delete()`, deletions registered `on_commit` and best-effort). A deliberate exception to the soft-delete convention; the Live Semester is refused inside `delete_semester()` itself, not just the view, and there is no export and no undo.
- `0009` — `SongRoleAssignment` (a **Standing Assignment**, semester-scoped per ADR 0001) was edited through the **per-Rehearsal** assignment grid on `/schedule/`, so a cell edit changed every rehearsal and the concert. **Narrowed by `0019`** (issue #499): casting moved to the Song, where the data's own scope matches the surface's, and this grid is Backups only. Still governing: do **not** "fix" the old scope mismatch with a `rehearsal` FK on `SongRoleAssignment` — that is ADR 0007's `Backup`; a past Rehearsal's grid (`date < today`) is not editable (`services.assignment_grid_is_editable()`); a Role column is only ever created by a `SongRoleRequirement` (ADR 0015), never written by the grid itself. Retired with `0019`: the "only a Rehearsal can compute the availability check" premise, `/songs/<pk>/` being read-only for assignments, and the Dress Rehearsal backstop.
- `0012` — the portal is a React/TypeScript SPA over a same-origin `/api/` JSON gate, reversing #168's no-bundler call but not the no-CDN rule, and re-affirming #123's no-DRF call by showing the alternative (`services.py`, endpoint-per-interaction) actually works at scale.
- `0013` — sign-in is email and password over Django's stock machinery, not #307's originally-planned passwordless emailed code — a reversal decided by #302, re-weighing a cost #307 had already named rather than correcting an error, and one that leaves the mailbox as the recovery ceiling either way. **Narrowed by `0018`**, which replaces the mailbox with an admin relaying a temp password by voice or text — the password-vs-passwordless call and everything else `0013` recorded stand unchanged.
- `0014` — what Roles a Person can play is a durable, person-level fact (`PersonRole`), not a per-`Membership` declaration — reverses the alternative `0001` rejected, but only for Role declarations; `Song` and `Membership` remain exactly as semester-scoped as `0001` describes.
- `0005` was **amended** by issue #341 to narrow its boundary to **attribution, not arithmetic** — an unattributed, admin-only aggregate count (the per-rehearsal pending-Conflict chip on `/schedule/`) is not the disclosure the original ADR guards against.
- `0015` — a `SongRoleAssignment` may only be created for a `(song, role)` pair that already carries a `SongRoleRequirement` (issue #439), reversing issue #213's "a Requirement confers no assignability" call: `count` is still a display target, never a cap, but a Requirement's mere existence is now a hard gate, checked at both the model (`clean()`/`save()`) and service (`apply_song_cast_edits()` for a cast, `apply_rehearsal_backups()` for a Backup) layers. The assignment grid's own ad-hoc "+ Add role" control (`addable_roles_for()`) is removed as a consequence — `addable_roles_for_song()`, the Requirements editor's "+ Add role requirement" control (issue #339), is the only remaining way to make a Role assignable.
- `0016` — `Role` gains a `group` FK to a new, admin-editable `RoleGroup` model (issue #457), replacing `frontend/src/lib/roleColumns.ts`'s retired `classifyRole()` keyword match as the source of the Setlist/Schedule cast tables' instrument-family columns. Admin-editable rather than a fixed enum, mirroring why `Role` itself is a table: a new Role needs a group to land in with no code change, falling back to a catch-all group (`RoleGroup.is_catch_all`) when nothing else fits. Deliberately leaves open how a future group-level Role Requirement count maps to concrete `SongRoleRequirement` rows — that's a follow-up ticket's decision, not this one's.
- `0019` — **casting is a Song-level act**: `SongRoleAssignment` is edited on `/songs/<pk>/`'s Cast mode and `/setlist`'s inline per-cell popover (one `SongCastEditBuffer`, two entry points), and the per-Rehearsal grid narrows to `Backup` + Running Order only — it still *displays* the standing cast as static text. Narrows `0009` by refuting its load-bearing premise: `services.song_cast_conflict_summary_for()` raises the loud-tier availability warning from the Song's side (one entry per *future* `RehearsalSong` the candidate would miss), reusing `_windows_overlap()`. Unique to this surface: the staleness anchor is `Song.updated_at`, not `Semester.updated_at`, so two admins casting two different Songs don't collide. The Dress Rehearsal's "Edit Rehearsal" control is gone outright and `assignment_grid_is_editable()` is now just `date >= today`.
- `0018` — email-based invite/reset (`invite_person()`'s emailed link, the self-serve forgot-password flow) is replaced by an admin-relayed temp password, revealed once in a synchronous admin response and relayed verbally or by text (issue #481, supersedes #381) — narrows `0013`'s decision to delivery mechanism only, real passwords and `is_login_rate_limited()` stand; decides the sole-active-admin lockout case via a `manage.py reset_password` break-glass command kept outside the web UI.

**Config** (`config/settings.py`) is entirely environment-driven via `django-environ`, reading `.env` locally / host-injected vars in production — no setting is ever a literal secret. Notable non-defaults: 30-day sliding session expiry (`SESSION_SAVE_EVERY_REQUEST = True`), TLS-everywhere settings gated behind `not DEBUG`, and object storage (`STORAGES['default']`) pointed at an S3-compatible backend (Cloudflare R2) per ADR 0004. There is no email setting left at all (issue #485, ADR 0018): `EMAIL_BACKEND`, `DJANGO_EMAIL_BACKEND`, `RESEND_API_KEY`, `SITE_URL` (previously required and validated at startup under `DEBUG=False`, to build absolute invite/reset link URLs outside request context), and `PASSWORD_RESET_TIMEOUT` are all removed — a temp password is relayed inline in a synchronous admin response, never as a link, so nothing in this project builds an absolute URL or issues a token with a lifetime to configure.

## Conventions

- **Per-app `factories.py`** (not under `tests/`) define `factory_boy` model factories other apps can import — `identity/factories.py:PersonFactory`, and one in `scheduling/factories.py` for every scheduling model. Add a factory here, not a static fixture, whenever a model needs test data.
- **Soft-delete over hard-delete** where history matters: `Role.is_active` retires a role with no deletion path (`RoleAdmin.has_delete_permission` returns `False`); the same pattern should be followed for any model where historical references must stay intact (see ADR 0002 for the reasoning that generalizes this).
- **Irreversible side effects go through `transaction.on_commit()`**, never inline inside a service function — sending mail, deleting an R2 object, calling any external API. Admin previews run the real save and roll it back (ADR 0008), so an inline side effect fires for real during a preview and cannot be undone. Registering it with `on_commit` makes rollback discard it for free.
- **A PR closes its issue with a keyword, not a title mention.** Every PR body carries `Closes #<n>` (one line per issue it resolves) in the `## Closes` section of `.github/pull_request_template.md`; `Refs #<n>` for an issue it touches but does not resolve. Two caveats: GitHub auto-closes **only on merge into `main`**, so a PR into a long-lived feature branch closes nothing and the final PR into `main` must carry the whole list; and **issue dependencies live on the issues**, set via each issue's Dependencies section, so a blocked issue clears itself when its blocker closes.
- **`AGENTS.md` covers the same ground** for other agents (structure, style, testing, commit/PR expectations). When you change a convention here, check whether it also needs changing there, so the two don't drift.
- **Docstrings are required on every function/method you add or modify** (views, model methods, factories, signal handlers, tests included) — CodeRabbit enforces an 80% diff-scoped coverage threshold on every PR. One line is enough for simple cases.

## Privacy constraint (read `CONTRIBUTING.md` for full detail)

This governs code, comments, commit messages, and test data, not just docs:
- No real member data ever, anywhere in the repo (names, emails, real setlists/dates/recordings) — synthesize everything via `factory_boy` + `Faker` at test-run time.
- No real credentials ever — they live only in Render env vars and GitHub Actions secrets. `.env.example` gets placeholder values only.
