# The portal is a React/TypeScript SPA over a same-origin JSON API, not a server-rendered Django app

The whole member-facing and admin portal — every page `docs/person-page-visibility.md` and every scheduling surface `CONTEXT.md` describes — is now a single-page React application built by Vite, served its own shell (`config/views.py:SpaIndexView`) that reads Vite's `manifest.json` per request, and backed by `/api/` endpoints under `config/api_urls.py`. Session cookies are unchanged: the SPA authenticates the same way the old templates did, over the same `identity` machinery, same-origin, no token in `localStorage` and no separate auth server. Issue #341's cutover deleted the server-rendered template tree, its vanilla-JS files, and the vendored Pico/HTMX/Alpine/SortableJS stack in the same PR that shipped this.

This reverses two prior decisions, and each reversal goes only as far as it says:

- **#168's no-bundler, no-node-toolchain call is reversed.** A Vite build and an ordinary `npm ci`-driven dependency tree now exist and are pinned by `frontend/package-lock.json`, replacing the old vendor-and-rename-on-bump procedure for four hand-downloaded files with ordinary npm tooling — Dependabot visibility included, for the first time.
- **The no-CDN rule is *not* reversed**, and stands on its original privacy reasoning, untouched by the stack changing underneath it: this is an auth-gated portal for a named group, and a CDN would announce every member's IP and referer to a third party on every page load, whichever build tool assembled the page. `scheduling/tests/test_static_assets.py` (rewritten by #341 against the Vite build rather than deleted, since its subject changed but its two invariants — a rename can't silently drop a pinned asset, and no page ever reaches a third-party origin — did not) still fails the build the moment a script, stylesheet, or `url()` inside a built stylesheet (the likeliest way a webfont re-enters) points off-origin.
- **DRF is still rejected.** #123 rejected it once already; the migration is the second, stronger occasion to reject it, because it proved the alternative works: the seam for a future API is `scheduling/services.py`/`identity/services.py`, endpoint-per-interaction, not a resource-shaped HTTP layer bolted on top of the ORM. Nothing under `/api/` is a `ModelSerializer` or a `ViewSet`; every endpoint is a thin view calling a service function and a hand-written serializer.

## Why the gate is two base classes, not per-endpoint checks or URL-prefix middleware

Every `/api/` view inherits `config/views.py:ApiView` (or, for an admin-only endpoint, `AdminApiView`, which layers `AdminRequiredMixin` ahead of it). The gate lives on the thing being gated — a base class every endpoint already has to subclass to exist — rather than on a URL-prefix middleware that would have to be kept in step with `config/api_urls.py` by hand, or on a per-view decorator a new endpoint could simply forget to apply. This is the same shape `BaseView`/`AdminRequiredMixin` already used for the pre-cutover portal (CLAUDE.md's "auth is structural, not per-view" rule), carried onto the wire rather than invented fresh.

## Why `ApiView` answers 401, not `LoginRequiredMixin`'s 302

`fetch()` follows a redirect transparently. An expired session hitting an endpoint that redirected to `/accounts/login/` would come back as an HTTP 200 carrying an HTML login page, and the client's `.json()` call would throw a parse error with nothing in it pointing at "your session expired" — a bug report with no visible cause. `ApiView.handle_no_permission()` overrides `LoginRequiredMixin`'s redirect with a JSON `401 {"error": "authentication_required"}` instead, so a session expiring mid-use is a status code the client can branch on, not a parse failure. `AdminApiView` does the parallel thing for a logged-in non-admin: a JSON `403 {"error": "admin_required"}`, never a redirect to a page that doesn't exist for that request shape.

## Why the envelope rides every response instead of being fetched separately

Every `/api/` response wears a `{"context": {...}, "data": ...}` (or, for a write, `{"context": ..., "ok": ..., "errors": ..., "non_field_errors": ..., "fallout": ..., "values": ..., "data": ...}`) shape. `context` carries the viewer, the viewing Semester and its status, the Live Semester, the full Semester picker list, whether a non-live-Semester warning should show, and (admin-only) the ambient pending-Conflict count — the same six facts the pre-cutover portal answered once per page via `scheduling/context_processors.py:semester_banner` plus a handful of per-view context keys. The reason it rides every response rather than being its own endpoint the shell fetches once is the same reason it was a context processor before: **a new endpoint cannot forget to carry it, because the envelope is the return type.** `ApiView.read_response()`/`write_response()` attach it themselves; there is no code path that returns a bare `data` payload. A separately-fetched "current context" endpoint would reintroduce exactly the failure mode issue #169 built the context processor to prevent — a page (here, an endpoint) that simply doesn't call it.

## Why a rejected Buffer is HTTP 200, not 400

A Pending Buffer that fails validation — a stale row, a blocked removal, a collision — is not a malformed request; it is a well-formed one whose answer is "no, and here is why", carried in the write envelope's `ok: false`/`errors`/`non_field_errors`/`values`. A `400` is reserved for a body that could not be parsed as JSON at all (`ApiView.parse_json_body()`'s `MalformedPayloadError`) or a `semester_id` that doesn't match the viewing Semester (a hard 409, since that is a stale-tab condition no amount of per-row error rendering can recover from). Every other rejection renders inline in the same request that would otherwise have succeeded, which is what lets a client show field-level errors without a second round trip.

## Why serializers are hand-written and `dataclasses.asdict()` is banned

Every `scheduling/serializers.py`/`identity/serializers.py` function names every field it emits. `dataclasses.asdict()`, `model_to_dict()`, or any other emit-everything helper is a rule that says "serialize whatever this object happens to carry" — and the day a new field lands on `Conflict`, on a Buffer dataclass, or on a Backup, it would ship to whatever payload touches that object with no line of code that ever decided that was safe. ADR 0005's whole boundary depends on the opposite default: **the unsafe thing (emitting a field) must require an action; the safe thing (leaving it out) must never require vigilance.** `scheduling/tests/test_prohibited_serializer_helpers.py` enforces the ban mechanically across both serializer modules, so this isn't a convention resting on code review alone.

## Why one endpoint per surface for reads, endpoint-per-interaction for writes — and why resource-shaped REST was rejected

A page like `/schedule/` fetches its entire read model — the timeline, the All-rehearsals list with its admin-only pending-count chips, the viewer's own availability — in one round trip from `GET /api/schedule/`, not three to five REST calls against `/api/rehearsals/`, `/api/conflicts/`, `/api/attendance/` assembled client-side. Resource-shaped REST was rejected for two reasons specific to this project: it costs 3–5 round trips where one currently suffices, and it pushes ADR 0005's per-field privacy verdicts and the `is_role_mismatch` derivation (ADR 0002) out of `services.py` and into the client, which is exactly the seam this project has always kept server-side. Writes are the opposite shape on purpose: `POST /api/setlist/preview/`, `POST /api/setlist/save/`, `POST /api/members/roster/roles/`, and so on are one endpoint per admin *interaction*, mirroring the Buffer → preview → apply surfaces they front rather than a generic `PATCH /api/setlist/` that would have to reverse-engineer which interaction a partial body meant.

## Why TypeScript types are hand-written rather than generated

`frontend/src/api/types.ts` names the same fields the serializers name, by hand, for the same reason the serializers are hand-written rather than derived: a generator pointed at the Django models would regenerate whatever fields exist, silently reintroducing the emit-everything problem one layer up the stack. Keeping both ends hand-written means a new field reaching the wire requires a person to add it in three places — the serializer, the TS type, and the component that reads it — and ADR 0005's boundary is a decision made three times rather than assumed once.

## ADR 0008's guarantee survives the wire

ADR 0008's actual promise was never "preview and save literally bind the same Django formset" — it was **"preview and save cannot disagree, because they run the same code."** That guarantee is unchanged by the migration: `config/views.py:AdminPreviewApiView` (`PreviewMixin` layered ahead of `AdminApiView`) still runs the real `apply_*()` inside `transaction.atomic()` and rolls it back, exactly as the pre-cutover `PreviewMixin` did; the wire adds one more place the guarantee could have quietly broken, closed by a `build_*_buffer_from_request()` function per surface (e.g. `scheduling/api_builders.py:build_setlist_buffer_from_request()`) that both the Preview and the Save endpoint call, so neither can construct its Buffer differently from a submitted body. `scheduling/tests/test_preview_save_buffer_identity.py` pins this by construction — it fails the moment someone forks the builder into two — and `scheduling/tests/preview_helpers.py:assert_preview_writes_nothing` is present against every `/api/…/preview/` endpoint, unchanged in what it checks: row counts, `Semester.updated_at`, `mail.outbox`, and that R2's `delete_object` was never reached.

## Consequences

- A node toolchain is a maintained dependency again, right after #168 removed one — accepted, not overlooked, because the alternative (twelve more hand-rolled Alpine files, one per surface this migration built) does not scale past the surfaces this project already has.
- An ordinary npm supply chain replaces four files with a version in their filename. `frontend/package-lock.json` being committed and every dependency resolving to exactly one locked version (`scheduling/tests/test_static_assets.py`'s `PinnedDependencyTests`) is the mechanical form of the same guarantee the old filenames gave for free.
- A bug in a shared `build_*_buffer_from_request()` function now affects Preview and Save at once — the intended trade-off, the same one ADR 0008 already accepted, now enforced one layer further out. **No second, naive preview implementation may ever be built for any surface**; that is the one thing that could route around `AdminPreviewApiView`'s rollback.
- `context.pending_conflict_count` and the per-rehearsal chip it's paired with on `/schedule/` are the first values this project's `/api/` layer emits that ADR 0005 had to be amended to allow — see the amendment on ADR 0005 for why an unattributed count is a different disclosure than the attribution that ADR guards.
- The old `/manage/` URL prefix that signalled "admin surface" in the deleted template tree has no client-side equivalent: SPA routes (`frontend/src/routes.tsx`) and `/api/` routes (`scheduling/api_urls.py`) carry no such prefix anywhere. Admin-ness is enforced the same way it always was — `AdminRequiredMixin`/`AdminApiView` on the server, and the shell's own nav rendering client-side — so the prefix was never load-bearing; it was a naming convention the URL gate never actually depended on.
- `scheduling/views.py`, `scheduling/urls.py`, `templates/base.html`, every scheduling template, the twelve vanilla-JS files, and the vendored stack are gone outright — not ported, not kept as a `legacy/` prefix, not commented out. `git log` is the only record of the old implementation from here on.
