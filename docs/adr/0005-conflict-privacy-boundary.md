# Conflict data is never rendered on a member-facing surface

A Person's `Conflict` rows — the free-text `reason` above all — are never rendered on any member-facing page, including the person page at `/members/<pk>/` and including when the viewer is an admin. Admins keep full access to Conflict data, `reason` included, through admin-only surfaces (today `ConflictAdmin`), because adjudicating a conflict and scheduling around it needs that context. The boundary is therefore drawn around the *surface*, not around the *viewer*: `/members/<pk>/` is a member-facing page even when an admin is looking at it.

We considered making `reason` owner-only even for admins (excluding it from `ConflictAdmin`), and considered a strict owner-only rule for all Conflict data. Both are behaviour changes rather than documentation of the existing boundary — the admin already reads `reason` today — and both misread which disclosure people actually object to. The concern a member has is that their bandmates will see *why* they're missing a rehearsal, not that the person building the schedule will.

## Amendment (issue #341): the boundary is attribution, not arithmetic

Issue #305's All-rehearsals sub-view puts an admin-only per-rehearsal **"N pending"** chip on `/schedule/` (built by #331) — a member-facing route. Read literally, the original paragraph above forbids this: it says Conflict data never renders on a member-facing surface, admin viewers included, with no exception named. That reading is too broad for what this ADR was actually defending. Re-read against the "concern a member has" sentence above, the thing being protected was always **attribution** — a Person's name, declaration type, declared time, free-text `reason`, verdict and adjudication note, none of which may reach a member-facing surface regardless of who is looking. An **unattributed aggregate count**, emitted only when the viewer is an admin and carrying no way to reach any individual row behind it, is a different disclosure and was already tolerated once before this amendment made it general: ADR 0006's flip refusal names a count of `Conflict` rows on a Rehearsal and nothing about any of them.

The chip is therefore permitted, with three conditions that keep it from becoming a second attribution channel:

- It is a **count only** — never a link to, and never a hover preview of, the rows it counts. The moment a count becomes a way to reach an individual row, it is attribution reached by another route, and this ADR's original rule applies to it in full.
- It is admin-only, the same gate every other Conflict-derived read on this page already uses.
- It does not appear on the sidebar nav item pointing at `/manage/conflicts/` (dropped there by #311/#328). That omission is now a **design** choice, not a privacy one: a count belongs where it is actionable — next to the Rehearsal it describes, where an admin can act on it immediately — not as an ambient badge glimpsed in passing on every page. Before this amendment the nav item carried no count because no count was allowed anywhere on a member-facing route; now it carries none because that is simply not where a count is useful, and the two reasons should not be conflated by a future reader.

`docs/person-page-visibility.md`'s field-by-field verdicts are **unchanged** by this amendment — every field that document governs is attributable, and this carve-out only ever applies to an unattributed sum.

## Consequences

- The owner reads their own Conflict data at `/schedule/`, not on their person page. (This was `/conflicts/` until that page was merged into `/schedule/`; the merge moved the surface, not the boundary.) `/members/<pk>/` renders no Conflict data for anyone, its owner included, so there is exactly one place this data is presented to a member and one owner-scoped query behind it.
- Derived attendance data (`Rehearsal.attendance_for`, `breaks_for`, `next_attended_rehearsal_for`, `attendance_suggestion_for`) is also absent from both `/members/` and `/members/<pk>/`. It is a partial inference of the same availability picture, so surfacing it per-person would undercut this boundary without touching a `Conflict` row. Self reads it on Overview and Schedule, anchored to a specific Rehearsal.
- Issue #130's admin edit layer on `/members/<pk>/` must not add a Conflict or attendance column. Its permission test is "is this surface member-facing", which is a property of the route, not of `request.user.is_admin` — an admin-only *column* on a member-facing page is the specific thing this ADR rules out.
- Admin Conflict adjudication stays on its own admin-only route (`/conflicts`, `/conflicts/<rehearsal_id>` — `/manage/conflicts/` before issue #341's cutover) rather than being folded inline into `/schedule/`. This is a deliberate exception to the otherwise-general move of admin affordances inline onto the member-facing pages they act on: a rendered `reason` is exactly what this ADR keeps off a member-facing route, and no `request.user.is_admin` check can make a member-facing route stop being one. `/schedule/` links admins out to that route; the link itself is unconditional and carries no count next to it — the amendment above puts the count on the individual Rehearsal it describes, not on the outbound link.
- An Adjudication's outcome and its optional admin note flow the *other* way across this boundary: an admin authors them, and the Conflict's owner reads them on their own row at `/schedule/`. That is not an exception to this ADR — the disclosure it guards against is a member's Conflict data reaching *other* members, and here the only reader is the Person the row is about. The note is nevertheless still Conflict data, so it is confined to the same single owner-scoped surface as `reason`, and it never appears on `/members/` or `/members/<pk>/`. An admin writing a note should know it is read by that member and by nobody else.
- The absence of an availability column on the roster is deliberate. A future reader will reasonably wonder why the band's own roster won't tell them who is coming to the next rehearsal; the answer is that band-wide convenience was traded away for it.
- (Issue #341) The one attributable field this ADR's carve-out does **not** cover is a Backup's `covering_for` name (ADR 0007) — an aggregate count of Backups would be permitted under this amendment on the same reasoning, but naming who is covering is attribution, and stays admin-only exactly as before.
- (Issue #341) `context.pending_conflict_count` in the `/api/` envelope (ADR 0012) is this amendment's other sanctioned aggregate: `null` for a member, an integer for an admin, and — like the per-rehearsal chip — a count with nothing behind it a member-facing response could use to reach an individual Conflict row.

The field-by-field verdicts for both routes live in [`docs/person-page-visibility.md`](../person-page-visibility.md).
