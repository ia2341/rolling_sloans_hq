# Person off-boarding is a reversible Deactivate, not a delete

`/accounts/manage/people/`'s retirement (issue #342) left two Person-lifecycle acts with nowhere to live: granting/revoking admin (issue #467), and taking someone off-boarded (issue #469). The second is **Deactivate** — `Person.is_active = False`, blocking login, immediately terminating any live session, and hiding the Person from current-facing views — never a delete. The row, email, password hash, historical Role Assignments, and Memberships are all untouched, and the act reverses via Reactivate. This differs from a Semester's own Delete (ADR 0011), which is a genuine hard, cascading, unreversed removal; Person off-boarding needed the opposite guarantee, since a Person is durable identity (ADR 0001) and historical assignments referencing them must keep rendering, not error.

## Consequences

- The "last admin" guard, `identity.services.other_active_admins()` (built alongside admin grant/revoke, issue #467), is reused as-is by Deactivate's own guard (`apply_person_deactivation()`, issue #469) rather than reimplemented: both count only Persons who are both `is_admin=True` and `is_active=True` — a deactivated admin's flag survives deactivation (admin status only ever changes by explicit action, never as a side effect) but doesn't count toward "someone must be able to log in and administer."
- `resend_invite()` (`identity/services.py`) refuses a deactivated Person (`PersonIsDeactivatedError`), added alongside its existing `has_usable_password()` check — "deactivated" is a dead end at the invite layer too, not just at login.
- Deactivation does not touch future-facing scheduling state (future Memberships, Role Assignments, Rehearsal Running Orders) — those surface to the deactivating admin as a warning, sourced from `future_scheduling_footprint_for()` (issue #468), a field added to `/members/:personId`'s read model specifically for this dialog.
- This is deliberately **not** a Pending Buffer/Preview/Fallout surface (ADR 0008's shape): there's no multi-field edit to accumulate, and the warning is a read of data the page already loads, not a rolled-back real save. "Fallout" (per CONTEXT.md) stays a term reserved for what a Preview computes; this warning is not that, and is not called by that name — it's a client-side confirmation dialog built from `future_scheduling_footprint`, not a server preview.
- Reactivation is the inverse with nothing to warn about: `apply_person_reactivation()` restores login and current-view visibility and nothing else, since nothing else was touched.
