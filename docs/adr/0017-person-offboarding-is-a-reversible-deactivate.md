# Person off-boarding is a reversible Deactivate, not a delete

`/accounts/manage/people/`'s retirement (issue #342) leaves two Person-lifecycle acts with nowhere to live: granting/revoking admin, and taking someone off-boarded. We're building the second as **Deactivate** — `Person.is_active = False`, blocking login, immediately terminating any live session, and hiding the Person from current-facing views — never as a delete. The row, email, password hash, historical Role Assignments, and Memberships are all untouched, and the act reverses via Reactivate. This differs from a Semester's own Delete (ADR 0011), which is a genuine hard, cascading, unreversed removal; Person off-boarding needed the opposite guarantee, since a Person is durable identity (ADR 0001) and historical assignments referencing them must keep rendering, not error.

This decision is recorded ahead of implementation (issue #342 is still open); nothing below exists in code yet.

## Consequences

- The "last admin" guard (to be built alongside admin grant/revoke, together with a self-revoke guard) will need to count only Persons who are both `is_admin=True` and `is_active=True` — a deactivated admin's flag should survive deactivation (admin status only ever changes by explicit action, never as a side effect) but must not count toward "someone must be able to log in and administer."
- `resend_invite()` (`identity/services.py`) will need an `is_active` check added — today it only checks `has_usable_password()` — so "deactivated" becomes a dead end at the invite layer too, not just at login.
- Deactivation should not touch future-facing scheduling state (future Memberships, Role Assignments, Rehearsal Running Orders) — those are meant to surface to the deactivating admin as a warning, but `/members/:personId`'s current read model (`serialize_person()` in `scheduling/serializers.py`) only carries viewing-semester data and has no future-semester Membership/Role-Assignment/Running-Order data yet. That warning will need a new field added to the read model, not just a read of what's already there — left for a human to resolve separately once built.
- This is deliberately **not** planned as a Pending Buffer/Preview/Fallout surface (ADR 0008's shape): there's no multi-field edit to accumulate, and the warning is meant to be a read of data the page loads, not a rolled-back real save. "Fallout" (per CONTEXT.md) stays a term reserved for what a Preview computes; this warning is not that, and should not be called by that name. Revisit whether this no-Buffer exemption still holds once the future-facing-state read model above actually exists.
- Reactivation is meant to be the inverse with nothing to warn about: it should restore login and current-view visibility and nothing else, since nothing else will have been touched.
