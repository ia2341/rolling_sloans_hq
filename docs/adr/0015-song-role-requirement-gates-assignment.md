# A SongRoleRequirement gates whether a Role is assignable on a Song

A `SongRoleAssignment` may now only be created for a `(song, role)` pair that already carries a `SongRoleRequirement`; `SongRoleAssignment.clean()`/`save()` reject one that doesn't, mirroring how ADR-0006 enforces the Dress-Rehearsal-conflict rule at the model+service layer (no DB constraint can reach through the `song`/`role` FKs to check for a Requirement row). `apply_song_role_assignments()` enforces the same rule for the Buffer write path, raising `MissingSongRoleRequirementError` — surfaced as `ok: false`, never a hard 400, matching every other rejected Buffer in this codebase. `assignment_matrix_for()`'s column derivation follows: a column is now every Role carrying a Requirement, full stop.

This reverses issue #213 (and the #151/#186 gate it restored the *un-gated* behavior against): `count` was, and still is, a display target rather than a cap on headcount, but the earlier design read that to also mean a Requirement's mere *existence* couldn't matter — that an admin should be free to assign any Role to any Song, whether or not a Requirement had ever been written for it, so the assignment grid grew its own "+ Add role" control that wrote a column with no backing Requirement at all. In practice this let an admin cast a Role a Song was never scored for at all (a Song with no Requirements could still gain assignees for arbitrary Roles), with nothing to catch a typo'd or accidental cast. Making the Requirements editor the *only* route to a new assignable Role costs an extra step (the Song page's own "+ Add role requirement" control) but keeps the two facts — "this Song needs a Bassist" and "so-and-so is playing Bass on it" — from diverging in either direction: an assignment can no longer exist for a Role the Song was never scored for, and it also can no longer be *the only reason* a Role reads as scored (the old orphan-column path).

The assignment grid's ad-hoc "+ Add role" control (`addable_roles_for()` and its `addable_roles` field/frontend counterpart) is removed outright as a consequence — it has nothing left to do once a column can only ever come from a Requirement. `addable_roles_for_song()` (the Requirements editor's own "+ Add role requirement" control, issue #339) is unaffected and is now the sole way a Role becomes assignable.

The gate holds in both directions: a `SongRoleAssignment` can't be *created* ahead of its Requirement, and it can't *outlive* one either. Removing a `SongRoleRequirement` — via `apply_song_role_requirements()`'s stale-role cleanup, the admin, or a direct `.delete()` — cascades to delete every `SongRoleAssignment` for that same `(song, role)` pair, via a `post_delete` signal on `SongRoleRequirement` (the same shape `PersonRole`'s `post_save`/`post_delete` receivers already use to keep `is_role_mismatch` in sync). A signal, not an override on the model's own `delete()`, because a queryset `.delete()` bypasses instance methods but still dispatches signals per row.
