# Unsaved admin edits preview by running the real save and rolling it back

An admin editing a bulk surface inline (roster, running order, assignment grid) needs to see, before committing, what their Pending Buffer would do: the slot times a reorder shifts, the Role Assignments a removal destroys, the Role Requirements it leaves unfillable, the mismatches a Role change newly flags. Per ADR 0003 and the way `RehearsalSong` persists its times, none of that is computable client-side.

**A Preview runs the real `apply_*()` service function inside `transaction.atomic()` and rolls it back.** It does not reimplement the derivation in JavaScript, and it does not extract it into pure functions over in-memory collections.

The alternative — pure functions over unsaved instances — was rejected on scope and on drift. Every derivation this Preview needs reads the database, not just the instance in hand: `RehearsalSong._prior_slots()` sums sibling rows to compute `start_time`/`end_time` and to detect a slot overrun; `SongRoleAssignment._compute_is_role_mismatch()` queries `MembershipRole`; `Rehearsal.attendance_for()`, `attendance_suggestion_for()` and `breaks_for()` each re-query from scratch. Making those pure means rewriting six read paths to accept a collection, and then maintaining two implementations of each — one over the Buffer, one over the database — for as long as the project lives. A Preview that can disagree with the save it previews is worse than no Preview. Running the save itself makes divergence impossible rather than merely unlikely; the endpoint is admin-only and low-traffic, so the cost of a rolled-back write is irrelevant.

## Every irreversible side effect must be registered with `transaction.on_commit()`

A rollback protects rows. It does not protect the outside world. Under this ADR a Preview executes the real save path, so an `apply_*()` that sends an invite email or deletes an R2 object *inline* would send and delete for real, during a Preview, unrecoverably.

**The rule is therefore project-wide and not specific to any one surface: an irreversible external side effect is never called inline inside a service function — it is registered via `transaction.on_commit()`.** Rollback then discards it for free, and the safe behaviour is the default rather than something each new side effect has to remember to opt into. A `preview=True` flag threaded through the services was rejected for exactly that reason: forgetting to check it fails silently and destructively, whereas forgetting `on_commit` fails visibly, during a Preview, before it can matter.

This was recorded before the fact. At the time of writing `on_commit` appears nowhere in the codebase; the post-commit R2 deletion and the invite email that motivate the rule are both still unwritten, so there is nothing to migrate — only a convention to hold.

## Consequences

- Preview endpoints are POST-only siblings of the surface they serve, never the surface's own URL distinguished by a header or a flag. A shared URL puts a real write one wrong header away; a separate route makes "does this write?" answerable from the route table.
- The rollback lives in a base view class, not in a `with` block copy-pasted per surface — the same structural-not-per-view reasoning that makes `BaseView` own `LoginRequiredMixin`. Alongside it, each preview endpoint's tests assert that a Buffer containing creations, mutations *and* deletions leaves every row count and `Semester.updated_at` untouched; the base class cannot catch a side effect that escapes the database, and the test is what verifies the `on_commit` rule rather than trusting it.
- `RehearsalSong.save()` raises `ValueError` on a slot overrun, and an exception inside `atomic()` poisons the transaction. Since a Preview of an *invalid* Buffer must still render (per-row errors, every submitted value preserved), the apply runs inside a savepoint whose failure is caught, and the outer block ends with `transaction.set_rollback(True)` rather than a sentinel exception — a sentinel raised through the stack is one stray `except Exception` away from becoming a real commit.
- A Preview does **not** take `_lock_semester()`. The lock serialises writes against `unique_song_position_per_semester`; a Preview keeps no writes, so it has nothing to protect, and holding a `select_for_update()` on the Semester row through a debounced drag would block every other admin's save. Two accepted costs: a Preview can be computed against a Semester that changes underneath it, which is what the `Semester.updated_at` staleness banner is for; and rolled-back inserts still consume primary-key sequence values, so ids have gaps. Neither is a bug.
- A Preview binds the *same* formset class to the *same* POST body the save endpoint takes — identical field names, management form and hidden `Semester.updated_at`. A JSON payload would mean a second parsing and validation path, reintroducing the drift this ADR exists to prevent.
- Two independent staleness questions are checked, and `updated_at` only answers the first. `Semester.updated_at` asks "did this Semester change since the Buffer was loaded?" — stale renders the Preview *with* a banner. The Semester id carried in the Buffer, cross-checked against the session-scoped admin selection, asks "is this even the right Semester?" — a mismatch hard-fails, on `apply_*()` as well as on Preview, because an admin with two tabs open can otherwise preview and then save one Semester's Buffer against another.
- A failed Preview is never allowed to block a save. The save recomputes and revalidates everything server-side anyway, so gating it on a transient 500 would lock an admin out of work already typed; the failure note says the Buffer is intact, which is the actual fear.
