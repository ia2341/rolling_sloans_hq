# Authentication is email and password over Django's stock machinery, not passwordless codes

Sign-in is email and password, invite-only with no self-registration, on the project's existing 30-day sliding session (`SESSION_COOKIE_AGE`, `SESSION_SAVE_EVERY_REQUEST = True`, unchanged by this decision). A `Person` never sets their own password from nothing: `invite_person()` creates the row with an unusable password and emails a one-time set-password link; the member chooses their own password from that link, and every sign-in after that is the member typing that password against Django's `ModelBackend`.

This ADR records a reversal within the map itself, so its most important job is to state the alternative that lost and why. **Issue #307 originally resolved this map toward passwordless six-digit emailed codes, and issue #302 reversed it.** For codes: a one-time secret has no permanent target to guess, and no member manages a credential at all — nothing to forget, nothing to reuse across sites. Against: a code makes *every* sign-in a round trip through email, where a password manager fills a password in one tap; #307 itself named this cost plainly — "desktop sign-in goes from one tap to a copy-paste" — and accepted it at the time. #302's reversal is a re-weighing of that named cost, not the discovery of an error in #307's reasoning.

## The ceiling is the mailbox either way

Say this plainly, because an ADR that oversells its own decision is worse than none: **the ceiling under either scheme is the mailbox.** Any portal with email-based account recovery can be taken by whoever holds the inbox — a code scheme proves this by construction, since the code *is* the credential, but a password scheme with a "forgot password" link is exactly as reachable through the same door. A password is a second, independent secret layered on top of that door. It raises the floor — an attacker who doesn't hold the mailbox now needs the password too, not just a moment of interception — but it does not move the ceiling. Nobody should read this decision as having solved account takeover; it narrows one path to it.

## Why the invite is still a link, not a code

#307's strongest objection to email-borne credentials was mechanical: a mail client hands a link to whatever browser it likes, on iOS frequently an in-app webview, so the session that link would produce lands somewhere that is not the member's own browser. **That objection is fatal for a link that produces a session, and merely cosmetic for a link that produces a password.** Under this decision the member opens the invite in whatever webview their mail client chose, sets a password there, closes it, and signs in normally in their actual browser of choice whenever they like — the artifact the link produced (a durable password) doesn't care where it was created. `resend_invite()` and the **Invite again** control on `/accounts/manage/people/` exist precisely because the artifact is durable but the *link* still expires: recovering from an expired invite is re-issuing the link, not extending its life.

## `PASSWORD_RESET_TIMEOUT` is one deliberately short global, not a longer invite-specific one

Django's `PASSWORD_RESET_TIMEOUT` (`config/settings.py`, explicitly stated as three days rather than left to Django's own default, which happens to also be three days) governs both the invite's set-password link and the forgot-password link, because both share one token route (`identity:set-password-confirm`, copy chosen by `has_usable_password()`). It was deliberately **not** raised to suit the invite: the same value would leave a multi-week account-takeover token sitting in an inbox for the reset case, and a mailbox that's been compromised for three days is already a bad week — three weeks is a different kind of bad. Recovery, not duration, is the answer for an invite that outlives its link: `resend_invite()` reuses the existing `Person` row (never creates a second one) and refuses a Person who already has a usable password, so an admin can't reset a working account from the roster by accident. This asymmetry falls out of Django's own `PasswordResetForm.get_users()`, which filters on `has_usable_password()` — forgot-password is structurally closed to a never-set-a-password account, and **Invite again** is what covers exactly that population.

`invite_person()` threads inline-vs-`on_commit` sending as a **parameter**, not a fork into two functions: rollback-on-send-failure (so a failed invite email leaves the address free to retry) and ADR 0008's on_commit rule for irreversible side effects cannot both be literally true of the same call path at once, and issue #336's Pending Buffer apply needs the `on_commit` behavior while the plain invite flow needs the inline one. Naming the trade-off in one function's parameter was chosen over maintaining two near-identical functions that would drift.

**No forced-password-change interceptor exists**, and none was built. It would need a flag on `Person` plus a gate on every authenticated request checking it — and the invite link already lets the member choose their own password once, so there is nothing temporary to force a change away from. **Emailing a temporary password was rejected for the same shape of reason**: a plaintext credential sitting in an inbox until somebody remembers to change it is strictly worse than a token-scoped link that expires on its own whether or not anyone acts on it.

## The two rate limits, and why the first is not optional under this decision specifically

`is_login_rate_limited()` and `is_auth_email_rate_limited()` (`identity/services.py`) are this project's first rate limits, both keyed on the submitted email address *and* the requesting IP independently (an OR, not an AND), both counted as a window of `LoginAttempt`/`AuthEmailRequest` rows rather than cached: `CACHES` is unconfigured, so Django's implicit fallback is a per-process `LocMemCache`, which would silently multiply any limit by the gunicorn worker count — a limit of five failures becomes five-per-worker with no error, no warning, and no way to notice short of an incident. Counting rows is exact across every worker with no new backend and no new dependency, at the cost of a database write per attempt.

The sign-in limit is **not optional under this decision** the way it might be under a lighter one: a one-time code dies on its own a short time after it's issued, so a guessing attack against it runs out of clock before it runs out of attempts; a password is online permanently, and every guess against it accumulates with no expiry ever pulling it out of reach. `is_login_rate_limited()` (ten failures in fifteen minutes, per address or per IP) is the substantive thing this decision has to build to get back what a code's own short lifetime gave the rejected scheme for free. The second limit — on outbound auth email (reset requests and resend-invites) — guards a different resource: an unauthenticated endpoint that triggers a third-party send is a way to burn Resend's quota and sending reputation, which would take down account recovery for everyone, not just the requester.

## Surface decisions: seven pages to three, and one surface moves inside the SPA

Django's stock auth machinery ships seven views' worth of pages; this project collapses them to three, all server-rendered outside the SPA: **sign in**, **request a password reset**, and **set a password from a token** (serving both the invite and the forgot-password confirm, with copy chosen by `has_usable_password()`). Four of the stock seven existed only to say "done" (`password_reset_done`, `password_reset_complete`, `set_password_complete`) or were the same operation under different wording, and were collapsed rather than kept as their own page. These three stay server-rendered rather than moving into the SPA, because they are the surface reached with **no session** — building them in React would mean shipping and maintaining a second, unauthenticated client mode for a portal that otherwise assumes a logged-in viewer everywhere. The accepted cost is that these three pages will drift from the SPA's design system over time unless someone deliberately duplicates its tokens into them.

**Change password moves into the SPA** (issue #333), on the member's own Person page, self-view only — the opposite placement from the three pages above, and deliberately so: it is the one auth act performed *with* a session rather than instead of one. `identity/api_views.py` calls `update_session_auth_hash()` after a successful change specifically so the request that just changed the password doesn't also invalidate the session making the request — Django cycles the session's auth hash on a password change by design, and skipping this call would silently log the member out of the exact tab they used to change it.

`ModelBackend` and a superuser password set out of band stay as a deliberate break-glass, reachable at `/admin/`. This matters concretely under this decision because `RESEND_API_KEY` sits on the recovery path: an outage at Resend, or a misconfigured key, means no member can complete a password reset or accept a fresh invite — but an admin with the break-glass password can still reach `/admin/` and act. #307's original objection to having two login surfaces — a member's code door and an admin password door with different rules — dissolves here, because under this decision both doors take the same kind of credential; there is exactly one authentication mechanism in the project, not two running in parallel.

## Consequences

- An invite link dies in three days and needs an admin's **Invite again** click to revive. Accepted: the click exists, is one button, and the alternative (a longer-lived token) is a longer-lived account-takeover window sitting in an inbox.
- The mailbox remains the recovery ceiling for both password reset and invite acceptance, with **no second factor** on top of the password itself — deliberately deferred as future work, not an oversight this ADR is unaware of.
- A member who is invited but never sets a password simply cannot sign in. This is correct behavior, not a bug, but it is invisible to an admin until they specifically look at that Person's invite status — `people_with_invite_status()` exists to make that look cheap, not automatic.
- Three server-rendered auth pages will visually drift from the SPA's Tailwind design system over time unless their tokens are kept in sync by hand; nothing enforces that mechanically.
- `LoginAttempt` and `AuthEmailRequest` rows accumulate forever with no retention policy — a future maintainer who wants to prune them should do so deliberately, not assume the two rate-limit functions need every historical row to function (only the current window does).
