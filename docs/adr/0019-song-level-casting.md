# Casting is a Song-level act; the Rehearsal grid narrows to Backups

`SongRoleAssignment` has always been `(song, role, person)` with no rehearsal FK — a fact about a Song, semester-wide by construction (ADR 0001), reaching every Rehearsal and the concert. ADR 0009 nevertheless put the only UI that could write one on the **per-Rehearsal** assignment grid, and spent most of its text explaining why that mismatch was worth paying for. Issue #499 reverses that call: casting moves to the Song — `/songs/<pk>/`'s new Cast edit mode, and an inline popover on `/setlist`'s own Role cells — and the Rehearsal grid narrows to the one thing that genuinely belongs to one evening, `Backup`.

This **narrows ADR 0009 rather than replacing it**, the same way ADR 0018 narrowed ADR 0013. ADR 0009's conclusion that a `rehearsal` FK must never be added to `SongRoleAssignment` still stands, and is in fact what makes this move safe: the table never meant "who plays this at this rehearsal", so relocating its editor changes no data, no migration and no semantics — only which page holds the affordance. Its shared conclusion with ADR 0007 — a Backup is its own model, anchored on `RehearsalSong`, scoped to one evening — is likewise unchanged, and is now the *whole* of what the Rehearsal grid writes.

## What ADR 0009's premise was, and why it no longer holds

ADR 0009 rejected a per-Song editor for two reasons.

The first was **decision context**: "the grid is where the information needed to make the decision lives" — which Roles are unfilled across the evening, who is already carrying three songs. This one was always a preference rather than a constraint, and the maintainer's own use disagrees with it: casting is decided once, per Song, usually while building the setlist, not while staring at one rehearsal's grid. The Setlist's cast table is where an admin actually looks when deciding who plays what, which is why this issue puts an editor *there* as well as on the Song page.

The second was the load-bearing one: **"availability fallout is only computable through a Rehearsal"**. A `Conflict` is declared against a Rehearsal and a `ConflictWindow` overlaps a `RehearsalSong`'s `start_time`/`end_time`, so ADR 0009 concluded a per-Song editor "structurally cannot raise" the loud-tier warning that assigning someone who can't be there produces.

That inference is wrong, and this issue is where it is corrected. A Song *has* Rehearsals — its own `RehearsalSong` rows — so the same two facts are reachable from the Song's side; they simply answer a differently-shaped question. Instead of "who, of everyone cast tonight, can't be here", a per-Song editor asks **"if I cast this person on this Song, which of its remaining rehearsals would they miss"**. `services.song_cast_conflict_summary_for(song, person, semester)` answers exactly that: one entry per **future** `RehearsalSong` of the Song where the person has a full `Conflict`, or a `ConflictWindow` overlapping that slot. It reuses `_windows_overlap()` verbatim, so the per-Song and per-Rehearsal checks can never disagree about what "overlap" means.

It is, if anything, the better warning of the two. The per-Rehearsal check told an admin about one evening; the per-Song summary tells them about every evening the decision they are making right now will touch, which is what a semester-wide decision deserves. It is rendered per candidate in the picker — a collapsed count, expandable to dates and reasons — and it never blocks: a conflicted candidate is castable exactly as before (ADR 0002's soft-flag posture, and the per-Rehearsal grid's own non-blocking loud tier).

## Consequences

- **`/songs/<pk>/` is no longer read-only for assignments.** ADR 0009 warned that two editors for one table would mean two Pending Buffers, two ADR 0008 preview pairs and two stale-save stamps. There are not two: the Rehearsal grid's `AssignmentEditBuffer` **loses** its `removed_assignment_ids`/`added_entries` fields entirely, and `SongCastEditBuffer` is the only Buffer that writes a `SongRoleAssignment`. One table, one editing Buffer — the Song page and the Setlist popover are two entry points into the same one, not two implementations.
- **The staleness anchor is `Song.updated_at`, not `Semester.updated_at`** — the only Buffer in this project that doesn't stamp the Semester. A cast edit is scoped to one Song, so two admins casting two different Songs concurrently have genuinely not collided; a Semester-wide stamp would reject one of their saves for a change it shares nothing with. `Song` gains an `auto_now` `updated_at` field for this, re-stamped by `apply_song_cast_edits()`.
- **The Rehearsal grid still *shows* the cast.** Its Role cells render the standing assignees as static text (with their away/mismatch markers) beside any Backup — that display is what makes "who is covering for whom tonight" legible at all. Only the write path narrowed: a standing assignee's pill carries no ✕, and the "+" picker offers a Backup section only.
- **The Dress Rehearsal's "Edit Rehearsal" control is gone outright.** ADR 0009 made it the backstop that kept *standing-assignment* editing reachable once every other Rehearsal had passed; with casting gone from this surface, that job no longer exists, and a Dress Rehearsal has no `RehearsalSong` row to anchor a Backup on or reorder (ADR 0003). `assignment_grid_is_editable()` loses its `is_full_setlist or` clause and becomes simply "not in the past"; the Dress Rehearsal is refused in one place, `_editable_rehearsal_or_404()`, which all three of the surface's endpoints already go through.
- **The Song page's "Casting happens on a rehearsal, not here" pointer is deleted**, along with the admin-only `next_rehearsal` key that fed it. It said the opposite of what is now true.
- **ADR 0015 is untouched and still gates everything.** A Role is castable only once a `SongRoleRequirement` exists for it; `apply_song_cast_edits()` raises the same `MissingSongRoleRequirementError`, surfaced as `ok: false`, and the Cast editor's rows *are* the Song's Requirements. ADR 0002's `is_role_mismatch` likewise still applies, computed by `SongRoleAssignment.save()` exactly as before.
- **ADR 0005's boundary does not move.** The one genuinely new disclosure is the picker's conflict summary, which carries a `Conflict.reason` — and it is served only by `SongCastPickerApiView`, an `AdminApiView`. The Fallout tiers name a Rehearsal date at most, never a reason, and no member-facing payload gained a field.

## Rejected alternatives

- **Keep both editors.** Rejected for the reason ADR 0009 itself gave: two write paths into one table is two Buffers, two previews and two staleness stories for the same rows, and the per-Rehearsal one would keep teaching the scope confusion this ADR exists to remove.
- **Give `SongRoleAssignment` a `rehearsal` FK so the grid's scope becomes true.** Rejected, emphatically, and for the third time: that is ADR 0007's question, answered with the `Backup` model precisely so this table can keep meaning one thing. Nothing here reopens it.
- **Drop the availability warning and accept a quieter editor.** Rejected: it is the one loud-tier signal this whole area has, and the per-Song formulation turned out to be strictly more informative than the one it replaces.
- **A per-Song editor scoped to "the next rehearsal" so the old check could be reused unchanged.** Rejected as a smaller version of the same mistake — a semester-wide decision judged against one arbitrary evening, with the arbitrariness now hidden instead of visible in the URL.
