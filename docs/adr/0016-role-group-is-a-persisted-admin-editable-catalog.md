# Role Group is a persisted, admin-editable catalog, not a fixed enum

`Role` gains a `group` FK to a new `RoleGroup` model (`display_order`, `is_catch_all`), seeded with the same instrument families the Setlist/Schedule cast tables already merged Roles into client-side: Vocals, Guitars, Bass, Drums, Keyboards, Saxophone, Trumpet, Violin, and a catch-all ("Other") every unmatched Role fell back to. Existing Roles are backfilled into these groups by the same keyword match the retired `classifyRole()` used, so current display behavior doesn't regress. `/api/schedule/` and `/api/setlist/`'s role legend entries now carry `group_name`/`group_order`/`group_is_catch_all`, and `frontend/src/lib/roleColumns.ts`'s `buildCastGridColumns()` merges Roles by that server-provided group instead of re-deriving it from the Role's name.

This issue named two open questions to settle before downstream work (a future group-level Role Requirement authoring surface) can build on this. Both are answered here.

**Is the group vocabulary fixed or admin-editable?** Admin-editable, via a real model rather than a code-level enum (a `TextChoices`, say). The reasoning mirrors why `Role` itself is a table and not an enum: an admin adding a new Role later (an unusual instrument, a new function) needs a group to land it in without a code change and a deploy, and `RoleGroup.is_catch_all` gives every such Role a home from the moment it's created (`services.default_role_group_for()`, used by both `create_or_reactivate_role()` and the `seed_dev_data`/`seed_example_semester` catalogs) even before an admin reclassifies it. The Django admin is the only editing surface for now — there is no SPA-facing Role Group management page — matching how `Role` itself is only ever retired through the Django admin today. `RoleGroup` follows `Role`'s soft-delete convention structurally rather than by adding its own `is_active` flag: `Role.group` is `on_delete=PROTECT`, so a group still classifying a Role can't be deleted at all, and `RoleGroupAdmin.has_delete_permission` returns `False` to match. Reclassifying a Role (moving it to a different group) or renaming a group are both ordinary edits, not full ADR-worthy decisions — nothing here treats the group assignment as any less mutable than `Role.name` itself.

**How does a future group-level Requirement count translate into concrete `SongRoleRequirement` rows?** Deliberately left unresolved — a follow-up ticket's problem, not this one's. What this issue's model *does* settle, and what that ticket can now build on: a `RoleGroup` has a well-defined membership (`Role.objects.filter(group=group)`), so a future "Vocals: 3" authoring surface has a concrete Role set to map its count against, whether that mapping ends up being "one canonical/representative Role per group" or something that spreads a count across every Role a group contains. This ADR takes no position on which of those a follow-up should pick; it exists only to record that a group's Role membership is now a real, queryable fact rather than something a future feature would have to invent its own classification logic to answer.

## Consequences

- `active_roles_for()`/`assignment_matrix_for()`'s Role queries carry `select_related('group')`, so a Role's group rides along with every other read that already serializes a Role legend entry — no new query shape per payload.
- `frontend/src/lib/roleColumns.ts`'s `classifyRole()` (and the `CastGridColumn`-building keyword match it powered) is deleted outright; `buildCastGridColumns()` now takes the API's `group_name`/`group_order`/`group_is_catch_all` fields directly. The Roster page's own filter-checkbox buckets (issue #366, `classifyRosterRoleName()`/`buildRosterFilterBuckets()`) keep their own, separate keyword match — `/api/members/`'s roster entries carry Role *names* only, with no Role id and so no group to read, and migrating that surface to the server-provided group is out of this issue's scope.
- A Role's `code` (`services.role_codes_for()`, still derived from `Role.name` and never persisted) is unrelated to `group` — a code is a per-Role scannable accelerator; a group is the column a Role's performers merge into. Nothing here couples the two.
